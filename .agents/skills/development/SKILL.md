# 开发流程

收到需求后，按顺序调研、判断大小、实现和验证。大需求先完成澄清、Spec 和 Plan，一起交用户审批。默认连续完成一个任务。

## 1. 调研

涉及已有代码时，围绕需求只读调研，不通读项目。先搜索文件和代码，定位与需求相关的内容，再沿调用链追踪：

1. 定位入口，梳理请求或操作经过的文件和函数。
2. 查找可以参考的类似功能，了解其分层、错误处理和实现风格。
3. 找到相关测试，了解测试的写法和覆盖内容。
4. 分析本次改动可能影响的地方。
5. 列出不确定的地方。

调研范围较大且任务可并行时，可使用 Subagent 分别调研，汇总带依据的结论。
简要汇报结果，结论标注相关文件路径和适用的函数名，不确定的写明不确定。
全新项目跳过已有代码调研。

## 2. 判断大小

根据规则是否清楚、影响范围、已有调用方和回退难度判断，并说明理由；拿不准按大需求处理。

- **小需求**：通常修改一两个文件，规则清楚且容易回退。说明预计修改的文件，然后直接进入实现。不单独写 Spec、Plan 或做 Review；范围扩大时重新判断。
- **大需求**：需要决定规则、跨模块或影响已有调用方等。将调研结论保存到 `docs/research/<功能名>.md`，供 Spec 和 Plan 引用，然后进入需求澄清。

## 3. 澄清、Spec 和 Plan（大需求）

### 澄清

- 只对影响功能行为的关键模糊、遗漏或矛盾提问，一次最多五个。
- 需要时给出推荐默认值和理由，由用户确认或否决。
- 没有需要用户决定的关键问题时，直接编写 Spec 和 Plan。

### Spec

按 `docs/templates/spec.md` 写入 `docs/specs/<功能名>.md`，包括：

- 目标和适用的接口定义。
- 可验证的验收标准，写明具体行为和边界。
- 范围外、待确认事项和验证方式。

未确认的内容列在待确认，不自行决定业务规则。

### Plan

根据 Spec 和 `docs/templates/plan.md`，将方案草案写入 `docs/plans/<功能名>.md`，按以下结构组织：

1. **依据**：关联的 Spec 和调研结论。
2. **文件清单**：新增或修改的文件及用途。
3. **关键实现方案**：重要设计选择、各部分职责和需要特别处理的地方。
4. **实施步骤**：按顺序列出步骤和每步的验证方式。
5. **验收与测试**：每条验收标准对应的测试。
6. **待决定事项**：不确定或需要用户决定的内容；没有则写“无”。

将 Spec 和 Plan 一起交用户审批，未经批准不修改业务代码；批准后直接开始实现。

## 4. 实现

有可测试行为的代码改动按 TDD 连续执行：

1. 大需求根据 Spec 的验收标准和边界值写测试；小需求根据已明确的需求和边界写测试。不要照着实现反推测试。
2. 运行测试，确认失败是因为预期行为尚未实现。
3. 编写实现并重新运行测试，确认通过。
4. 需要时在测试保护下重构，并保持测试通过。

测试失败时，分析是测试、实现还是环境导致。测试本身有误可以修正，但要说明原因和依据；不得为通过而弱化断言、删除或跳过测试。

文档、注释等改动采用适合的检查，不强制写测试。大需求按批准的 Plan 实施；必须超出文件清单，或发现 Spec、Plan 有问题时，先停下说明并等待用户决定。

## 5. 验证和汇报

1. 代码改动运行 `make check`；遵守 AGENTS.md 中的 Windows 和替代命令约定。
2. 根据 Spec 或任务需要启动服务并发送真实请求，对照预期核对状态码和响应，报告实际请求和响应，结束后关闭服务。
3. 检查 `git status`，汇报改动文件、测试失败的实际输出和实现后的结果、其他验证结果及限制。大需求说明是否超出 Plan。
4. 完成后停下供用户检查和提交。

变异检查仅按用户要求进行：先确认工作区干净，结束后只恢复临时修改的文件。

## 6. Review

大需求实现并提交后，由用户开新会话发起 Review。用户根据审查结果决定哪些问题修复、哪些记入 backlog、哪些忽略。

## 7. 审查后的修复

用户确认 Review 问题后，回到原开发会话修复：

1. 只修复用户确认的这一批问题；范围外问题按用户决定记入 `docs/backlog.md`，误报忽略。
2. 对每个问题先复现并用失败测试覆盖，再修复并运行测试。
3. 完成整批代码修复后运行 `make check`，统一报告结果，供用户检查和提交。

如果修复需要改变需求或方案，先停下询问用户。
