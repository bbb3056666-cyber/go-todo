AI协助开发总流程
基础概念 + 项目地基：
1. Agent（智能体）
普通AI：让ChatGPT 写代码，它给你一段文字，你自己复制粘贴；让 agent 写代码：它会自己读你的项目文件、改文件、跑命令、看报错、再改，直到完成。
它的工作循环是：读代码 → 制定计划 → 动手改 → 运行验证 → 根据结果再调整。
和"纯聊天"的关键，就是有没有给这个循环配上规则、验证和护栏。后面所有模块都是围绕这件事。

2. Prompt（提示词）
发给 AI 的任务描述。 比如"帮我加一个创建待办的接口"就是一个 prompt。
通俗类比：prompt 像你给新同事派活的口头交代。交代得含糊（"弄个接口"），同事就会乱猜；交代清楚（背景、目标、约束、怎么验收），活就干得准。

3. Context（上下文）
AI 当前"看得见"的所有信息：你的 prompt、它读过的文件、命令输出、之前的对话。
类比：AI 的工作台，桌面大小有限。堆满了无关文件，真正重要的东西就被挤掉，质量下降。所以后面会反复讲"别乱塞"、"每个任务开新会话"。

4. AGENTS.md（重点）
是什么：放在项目根目录的一个普通文本文件（Markdown 格式，.md 结尾），里面写给 AI 看的项目说明，每次启动会话它都会自动读。
长什么样：一份纯文本清单，包含常用命令，项目结构，代码约定，工作方式，禁止事项等
AGENTS.md 是跨 agent 通用的开放标准，Codex、Claude Code、Gemini CLI 等都能读。

5. Makefile
一个叫 Makefile 的文件，把常用命令起个短名字存起来，用 make 命令调用。不用每次敲 go test ./... -race -cover，只要敲 make test。
Makefile 把 lint、test、build 封装成统一入口，AGENTS.md 里只引用 make check。这样 AI 自测、本地、CI 流水线用的是同一套验证标准

6. Skill、Hook、MCP
AGENTS.md：希望 AI 知道什么。
Skill：希望 AI 怎么做。可复用的"操作手册"，比如"代码审查清单"。Codex 里用 SKILL.md 文件定义，平时只加载名称和描述，真正用到时才加载全文，省上下文。
Hook：希望 系统到了某个节点自动做什么。在 AI 工作过程中的某些时刻自动触发的脚本，比如"改完代码自动跑测试"。
MCP：希望 AI 拥有外部能力。让 AI 连接外部系统（数据库、GitHub 等）的标准接口。

Spec + Plan部分概念：
1. Spec（规格说明）
一份写清楚"要做什么、不做什么、怎样算做完"的需求文档，是放在项目里的一个 .md 文件。
包含：目标、接口定义、验收标准、范围外、验证方式

2. 验收标准
Spec 里的一部分，用可以被验证的句子描述完成条件。
差的写法："接口要健壮"；好的写法："title 为空时返回 HTTP 400，body 里 code 为 40001"

3. 范围外（Non-goals）
Spec 里的一部分，明确写出这次不做的事。AI 有"热心过度"的毛病，你让它做创建接口，它可能顺手把数据库、鉴权、分页都加上。写明范围外就是给它划边界。

4. Plan模式
让 AI 只出实施方案，不改任何文件。方案里会说明：打算改哪些文件、分几步、怎么验证。看完符合 Spec，再放行执行。

5. 反向提问
只有一个模糊想法时，让 AI 来提问，把没想到的细节逼出来（比如空标题怎么办、ID 怎么生成）。比自己苦思冥想漏洞更少。
遇到不确定的业务细节，可以让 AI 给出推荐默认值和理由，我只做确认或否决。

6.SDD（Spec-Driven-Development）
规格先行，以规格说明作为需求的唯一来源，先编写并评审 Spec，再据此设计方案、拆分任务、实现与验证，规格与代码保持同步

            Spec	                                Plan
回答的问题	做什么？做到什么程度算做完？	            怎么做？
谁来定	    需求方决定，AI 整理	                    AI 给出，我审查是否满足 Spec
内容	        目标、接口定义、验收标准、范围外、验证方式	改哪些文件、实施步骤、测试怎么写
关注点	    行为和结果	                            实现过程
稳定性	    相对稳定，需求不变就不变	                可以反复调整

需求（一句话 / PRD / 工单）
│
├─ 第 0 步：了解现状，判断大小
│   ├─【AI】只读调研：找入口、调用链、可参照的实现（定向，不通读）
│   │       结论标注文件路径和函数名，不确定的写"不确定"
│   └─【AI】判断大小并说明理由
│
├─ 【小需求】改一两个文件、规则清楚、可回退
│   ├─【AI】说明要改哪些文件（比预期多 → 升级为大需求）
│   ├─【AI】测试先行：先写失败的测试，再改代码
│   ├─【AI】make check，列出改动文件 ⏸
│   └─【我】对账 → 看 diff → 提交
│
├─ 【大需求】有规则要决定 / 多文件 / 跨模块 / 影响调用方（别处已经在使用，而不是纯新增）
│   │
│   ├─ 1. 反向提问（澄清）
│   │   ├─【AI】存调研结论 → docs/research/
│   │   └─【AI】反向提问 ⏸
│   │       └─【我】回答；答不上就让它给默认值，我只否决不合理的
│   │
│   ├─ 2. Spec（做什么，SDD）
│   │   ├─【AI】按模板写：目标、接口定义、验收标准、范围外、验证方式 → docs/specs/ ⏸
│   │   └─【我】审：验收标准可验证？范围外写了？有无自作主张？ → 批准
│   │
│   ├─ 3. Plan（怎么做）
│   │   ├─【AI】只出方案，不改代码：文件清单、步骤、验收标准对应的测试 ⏸
│   │   └─【我】审：有无意外文件？符合分层约定？ → 批准
│   │       └─【AI】存 → docs/plans/ ⏸（等我说"开始实现"）
│   │
│   └─ 4. Execute（TDD）
│       ├─【AI】按 Plan，测试先行：先贴失败输出，再写实现
│       ├─【AI】make check
│       ├─【AI】启动服务，按 Spec 发真实请求，贴出实际响应，关闭服务
│       ├─【AI】列出改动文件，说明是否超出 Plan ⏸
│       └─【我】对账（git status、go.mod）→ 自己复跑 make check → 审关键代码diff → 变异检查 → 提交
│
├─ Review
│   ├─【AI】新会话，只读，依据 review-checklist.md
│   │       先判清单哪些适用，再只审适用的 → 分级报告 ⏸
│   ├─【我】逐条分类
│   │    ├─ 真问题且在范围内 ──→ 修
│   │    ├─ 真问题但在范围外 ──→ 记入 docs/backlog.md
│   │    └─ 误报 / 过度设计 ───→ 忽略
│   └─【AI + 我】修复
│          ├─【AI】一次一两条，先写失败的测试，再改代码，make check ⏸
│          └─【我】对账 → 复跑 → 提交 → 下一条
└─ Ship
    ├─ 推送分支 → 提 PR
    ├─ CI 在干净机器复跑检查
    ├─ 同事 Review
    └─ 合并

我需要做的：大小需求，回答澄清，审 Spec，审 Plan，审 Execute，审 Review 范围、问题、修复；
机械检查交给 Makefile 和 CI。

Research：
    这一步的目的是完善上下文，做法不是读完项目，而是找到相关的最小集合，否则窗口有限，塞满无关代码，真正重要的东西反而被挤掉，生成质量下降。
    如果是新项目，只需要让 agent 读 AGENTS.md、Makefile、go.mod 这些全项目可复用的文件
    如果是老项目，不是让它了解整个项目，而是围绕本次任务获取信息
        1.围绕任务定位：让 AI 用搜索（搜索服务可以通过MCP接入）定位，而不是无脑全读，目标大致是入口在哪、调用链怎么走、有没有类似功能可以参考、相关测试在哪。
          调研可能会读取大量内容，为了不挤占主会话上下文，可以让Subagent在独立的上下文并行调研，只把结论传给主会话。
        2.找范例：找一个相似的现有功能，让它照着写，风格、分层、错误处理、测试写法自然和项目一致，比自己写一堆规则更可靠
        3.带证据 + 落文件：结论必须标注文件路径和函数名，防止幻觉；
        4.调研结果存成文件，比如docs/research/order-remark.md，Spec 和 Plan 直接引用，新会话也能直接复用
    prompt：
    先不要修改任何代码。围绕这个任务做调研：【目标任务】
    回答：
    1. 请求从入口到数据库的调用链，经过哪些文件
    2. 有没有相似功能可以当范例
    3. 相关测试在哪、怎么写
    4. 这次改动可能影响哪些地方
    5. 不确定的地方
    要求：每个结论标注文件路径和函数名；只读相关文件，不要通读项目；
    结果保存到 docs/research/<任务名>.md。

Spec + Plan：
    这一步的目的是把"做什么"和"怎么做"分开定下来，并且落成文件，避免需求停留在对话里漂移、丢失。
    第一步：接需求，AI 反向提问
        需求来源可能是一句话（小改动，比如一个小接口，加个字段）、工单或需求文档（PRD），
        处理方式都一样：让 AI 做需求评审，找出模糊、遗漏、矛盾的地方，反向提问，把没想到的边界逼出来。
        遇到不确定的业务细节，可以让 AI 给出推荐默认值和理由，我只做确认或否决。
        prompt（一句话需求）：
            我想给这个项目增加"创建待办"的 HTTP 接口。
            先不要写代码，也不要出方案。
            请你扮演需求评审，向我提问，帮我把需求澄清到没有歧义。
        prompt（有需求文档）：
            阅读 docs/requirements/xxx.md。
            先不要写代码，也不要写 Spec。
            找出这份需求里模糊、遗漏或前后矛盾的地方，

    第二步：落成 Spec
        把结论落成 Spec 文档，包括：目标、接口定义、验收标准、范围外、验证方式
        prompt：
            根据我们刚才的讨论，把需求写成规格说明，保存到 docs/specs/create-todo.md。
            必须包含：目标、接口定义、验收标准、范围外、验证方式。
            只创建这一个文件，不要改其他文件。
        我审三点：验收标准是否可验证、范围外是否写清、有没有它自作主张加的需求。

    第三步：落成Plan
        在 Plan 模式下让它只出方案、不改文件，我重点审查文件清单有没有超出预期、有没有违反项目约定。
        prompt：
            请阅读 docs/specs/create-todo.md 和 AGENTS.md，
            然后只给出实施方案，不要修改任何文件，方案审查通过后，保存到 docs/plans/<功能名>.md。
            方案需要包含：
            1. 计划新增或修改的文件清单，每个文件说明用途
            2. 实施步骤，按顺序，每步可独立验证
            3. 每条验收标准对应的测试
            4. 你不确定或需要我决定的地方
        Plan 出来后我会对照清单审：文件清单是否越界、依赖方向是否符合分层、每条验收标准有没有对应测试、有没有它自作主张加的功能。

    为什么要写 Spec，不直接说需求？
    对话会漂移、新会话也没法复用；Spec 是持久的、能进 git、能直接转成测试，AI 在新会话里也能读。

    范围外有什么用？
    防止 AI 过度发挥，控制改动范围，也方便 review。

    方案里出现意外文件怎么办？
    先让它解释理由，不合理就剔除，这是发现 AI 偏离的第一道关口。


Execute部分概念：
1. TDD（Test-Driven-Development）测试驱动开发
测试先行，先编写会失败的自动化测试，再编写刚好能让测试通过的实现代码，最后在测试保护下重构。
核心循环叫 Red → Green → Refactor。
Red（红）	        先写测试，运行后失败，证明测试有效且功能尚未实现
Green（绿）	        写最少的实现代码让测试通过
Refactor（重构）	    在测试保护下整理代码，保持测试仍然全绿

2. Checkpoint（检查点）
每完成一小步就停下来，由你确认。本模块的核心节奏就是：一步 → 验证 → 提交 → 下一步。

3. Commit（提交）
git commit 就是存档。每步一个存档，出错了可以回到上一个存档，不会全盘报废。

4. Diff（差异）
git diff 显示"相比上次存档，改了哪些行"。你审代码主要就是看 diff，不需要通读整个项目。

5. 回滚（Rollback）
AI 改坏了，退回到上一个存档。

Execute：
    这一步的目的是让 AI 的产出可验证、可回退。Spec 和 Plan 管做什么、怎么做，Execute 管做出来的东西能不能信。

    核心循环（Red → Green → Refactor）：
        Red：先写测试，运行后失败，证明测试有效、功能尚未实现
        Green：写刚好让测试通过的实现
        Refactor：在测试保护下整理代码，保持全绿
    "最少实现"指每一轮只让当前这一个失败测试通过，然后再加下一个测试，
    它会再次变红，逼出新的代码。测试清单来自 Spec 的验收标准，不是照着代码反推。
    测试的价值不在静止时全绿，而在以后改坏时会变红。

    TDD 在 AI 场景的价值：测试先行，让测试成为独立于实现的验收标准，避免 AI 写完代码再补测试，自己出题自己答。
    和 SDD 的关系：SDD 管需求层（做什么），TDD 管实现层（做对了吗）。
    Spec 的验证标准在 Plan 里对应测试，这就是 SDD 到 TDD 的交接。

    按任务大小选流程：
        小改动（改字段、修小 bug）：一条 prompt 说清楚，让 AI 测试先行，跑 make check，看 diff，提交
        中等以上功能（新接口、新模块）：完整走 Spec、Plan、执行
        判断标准：改动能不能一眼看完

    第一步：确认起点
        git status：在功能分支，工作区干净
        git log：Spec 和 Plan 已提交，这是安全存档点
        新开会话（上下文干净）

    第二步：发执行指令
        prompt：
            阅读 AGENTS.md、docs/specs/create-todo.md、docs/plans/create-todo.md，
            按方案的实施步骤依次实现。
            1. 按测试先行的方式做：每个模块先写测试并运行，确认失败，并把失败的输出贴出来，再写实现，直到测试通过
            2. 测试清单来自 Spec 的验收标准和边界值，而不是照着代码写
            3. 测试失败时，先分析原因，根据 Spec 判断是实现错误、测试错误还是环境问题。允许修正有误的测试，但必须说明原因和依据；不得仅为通过测试而弱化断言、删除或跳过测试。需求有歧义时先问我。
            4. 不要修改 Spec、Plan、AGENTS.md、Makefile、go.mod
            5. 不要执行 git commit，由我来提交
            6. 全部完成后运行 make check，贴出实际输出，并列出所有改动的文件，并说明有没有超出方案文件清单的改动

    第三步：ai完成后我做一次验收
        1. 对账：改动文件是否和 Plan 的文件清单一致
        2. 复跑：自己终端跑 make check
        3. 审核关键代码：挑最容易出错的几处扫一眼
        改动太大看不过来时，才改成每个模块停一次。

    第四步：提交，再做变异检查（顺序不能反，否则 restore 会丢掉没提交的代码）
        git add . ; git commit;
        变异检查：故意改坏一处实现，运行 make test，对应测试应该变红。
        不红说明这条规则没被测到。验完 git restore . 撤销。

    第五步：实际请求一次
        起服务，用 curl.exe 发合法、空标题、带 done 字段的请求，
        核对状态码和响应；重复提交确认 ID 不同。

    出问题怎么办：
        场景	                命令
        还没提交，想全部放弃	git restore .；新文件先 git clean -nd 预览，再 git clean -fd
        已提交，想退回	    git reset --hard HEAD~1（会丢掉那次提交，确认再用）
        越界改了文件	        git restore 该文件路径，告诉它"不在方案内"
        它说通过但你复跑失败   把输出贴给它，让它先定位原因再改，不要让它盲目重试

    为什么不一次让 AI 做完不管？
    短期快，但出错时很难定位，也容易引入没人看过的代码；
    小步加检查点，整体更可靠，回滚代价也小。

    为什么提交由我来做？
    每个存档点都经过人的审查，AI 的提交不等于经过验证。

Review：
    目的：Execute 保证代码符合 Spec、测试能通过，Review 找的是测试没覆盖到的问题：安全、并发、健壮性、可维护性
    两层：
        AI 自查：新会话审 diff，先过一遍机械问题
        人工把关：我判断哪些是真问题、哪些是误报，并对结果负责。

    为什么用新会话审，不让写代码的会话自查？
        写代码的会话带着自己的思路和假设，容易觉得没问题；
        新会话只看到 diff，没有这层偏见。

    AI Review 的局限：会误报，也会漏报，结论必须由人判断。

    审查依据：
        把通用清单固化成仓库文件 docs/review-checklist.md
        8 类：需求对齐、边界与异常、并发与幂等、数据库、安全、性能与健壮性、可维护性、测试与可观测性
        一开始覆盖后端通用场景，后续根据实际项目拓展，并把团队踩过的坑持续往里加（比如线上事故复盘后补一条）。
        例如：数据库类里的索引、事务、迁移回滚；金融业务可加对账和资金精度。
        好处：清单只维护一处、不会漏项、团队共用、有版本记录。

    流程：
        1. 新开会话，只读，不提交
        2. 让 AI 读清单，先逐项说明适用或不适用及原因，再只审适用的（清单越全，这一步越重要，防止 AI 编造不存在的问题）
        3. 我先检查它的"不适用表"，排除得对不对；
           按流程确定待修复问题：
               真问题（能复现，读代码确认确实存在）且在需求范围内 → 要修
               如何确定：读代码、写测试复现、让 AI 给出触发问题的输入
               真问题但在范围外 → 记在待办，不在这次修
               误报或过度设计 → 忽略，但需要有忽略理由
        4. 只修我认可的，每次一两条，先补会失败的测试再修（TDD流程）
        5. 对账（git status）、自己跑 make check、看 diff、提交

    审查 prompt：
        你是代码审查员。只读，不要修改任何文件，不要执行 git commit。
        审查当前分支相对 main 的全部改动，对照 <Spec> 和 AGENTS.md。
        审查依据：docs/review-checklist.md。
        分两步输出：
        第一步：逐项列出清单里哪些条目适用、哪些不适用，不适用的写一句原因。
        第二步：只审适用的条目。按 高/中/低 分级，每条给出文件、函数、问题和修复建议。
        不确定的标注"不确定"，不要为凑数编造问题。

    为什么清单要做成文件，不每次手写 prompt？
        手写容易漏项，也没法团队共用；文件可以进 git、持续迭代，
        后续可以升级成 Skill，同一份内容加触发说明即可一句话调用。

    修复prompt:
        只修复这一个问题：【问题描述】
        要求：
        1. 先补一个会失败的测试，运行并贴出失败输出
        2. 再修改代码，让测试通过
        3. 只改【允许的范围】，不要改 Spec 和其他文件，不要提交
        4. 完成后运行 make check，贴出结果，列出改动的文件


Skill 与 Hook：
    Skill：文件夹加 SKILL.md（必须有 name 和 description），把某类任务的做法固化。
        渐进式披露：平时只加载名称和描述，用到才读全文，省上下文。
        description 是触发器，要写清适用范围和边界。
        位置：仓库的 .agents/skills/<名字>/SKILL.md，团队共享。
        Skill 的两种触发方式：
            显式调用：消息里点名，如 $review-checklist
            隐式调用：AI 根据 description 判断任务匹配，自己启动
            默认两种都开；在 skill 目录下的 agents/openai.yaml 里设置 policy.allow_implicit_invocation: false 可关闭隐式调用，显式调用仍然有效。
            取舍：重流程、由我决定时机的（如 Review）关；轻量、希望 AI 自己想起来的（如固定排查步骤）开。

    Hook：在 AI 工作流的事件点自动执行命令（PreToolUse、PostToolUse、Stop 等），
        配在 .codex/hooks.json。本项目：Stop 时自动跑 make check。
    分工：规则写 AGENTS.md（建议），流程写 Skill（按需），
        必须执行的动作交给 Hook（强制）。
    解决的问题：把手工重复的动作（贴长 prompt、手跑检查）固化，
        人只保留需求评审、方案评审、diff 评审三个判断。


Ship：
    目的：让代码安全地从个人电脑进入团队主分支。
    路径：推送分支 → 提 PR → CI 自动检查 → 同事 Review → 合并
    PR：
        对团队说"这个分支做完了请审查"的页面，含改动、说明、评论、检查结果。
        PR 描述 prompt：
            阅读 Spec、Plan
            以及当前分支相对 master 的提交记录（git log master..HEAD --oneline）。
            写一份 PR 描述，直接输出在对话里，不要创建文件，不要修改任何文件。

            包含这几部分：
            1. 做了什么（2-3 句）
            2. 为什么做（指向 Spec）
            3. 怎么验证的（测试、覆盖率、变异检查、实际请求）
            4. Review 发现及处理


    CI：
        推送后在干净机器上自动跑格式、静态检查、测试，是第三方裁判。
        配置在哪：
            项目\
            └── .github\
                └── workflows\
                    └── ci.yml
        ci.yml 内容：
            name: CI     这套检查的名字，显示在 PR 页面上

            on:                      触发条件
              pull_request:          有人提 PR 时触发
              push:                  推送时触发
                branches: [master]   推送到master时触发

            jobs:
              check:                                一个job是跑在同一台机器上的一组step，不同 job 跑在独立runner上，job 间默认并行，可以使用needs让job有依赖（仍是跑在不同runner，跨job传文件用upload-artifact，download-artifact，传小数据用outputs）
                runs-on: ubuntu-latest              runs-on: 指定执行 job 的机器
                steps:                              job的步骤，串行执行
                  - uses: actions/checkout@v4       uses：调用现成Actions
                  - uses: actions/setup-go@v5
                    with:                           给uses配置参数
                      go-version-file: go.mod       参数名：参数值
                  - name: Check formatting          name：给步骤起名，显示在github页面上
                    run: test -z "$(gofmt -l .)"    run：执行普通命令，这里在检查有没有格式不规范的文件，test -z表示字符串长度为0是为真，gofmt -l . 列出格式不规范的文件名，格式都对就什么都不输出，$(...) 把输出结果取出来
                                                    任何一个 run 的命令返回失败，这一步就标红，后面的步骤默认不再执行，整个 Job 标红，PR 页面显示红叉。
                  - name: Vet
                    run: go vet ./...           静态检查
                  - name: Test
                    run: go test ./... -race -cover
        常用写法:
            env:	            设置环境变量
            needs: build	    这个 Job 要等 build Job 成功后才开始（否则 Job 默认并行）
            strategy.matrix	    同一套步骤用多个版本各跑一遍，比如 Go 1.22 和 1.23
            if: failure()	    条件执行，比如失败时才执行某步
            ${{ secrets.XXX }}	读取仓库里存的密钥，日志里会自动打码
            ${{ github.sha }}	读取内置信息，这里是当前提交的编号
            concurrency	        同一分支新的运行启动时，取消旧的还在跑的，省资源
            timeout-minutes	    给 Job 设置超时，防止卡死

        一次运行如何发生：
            git push 或提 PR
               ↓
            GitHub 发现事件，匹配到 ci.yml 的 on 条件
               ↓
            分配一台全新的 ubuntu 机器
               ↓
            checkout → setup-go → 格式 → vet → 测试，逐步执行
               ↓
            全部成功 → PR 页面绿勾 ✔　　任何一步失败 → 红叉 ✘

        两个安全相关的常识：
            密钥只放在 Secrets 里，绝不写在 yml 里，否则等于公开
            使用第三方 Action 有供应链风险，更严格的团队会把版本固定到某个具体的提交编号，而不是 @v4 这种可变标签

        不同分支上的.github不一样怎么办： 文件跟着分支走，用哪份取决于事件
            push 用被推送分支的；pull_request 用合并预览版本；pull_request_target 用目标分支的；schedule 用默认分支的。
            风险：PR 可以改 CI 绕过检查。
            防护：CODEOWNERS 保护 .github 目录、分支保护要求必须通过的检查、组织级强制 workflow。
            管理：CI 配置变更单独提 PR，尽快合入主分支，避免长期分叉。

流程主线：
    地基：AGENTS.md（规则） + Makefile（统一验证命令）
       ↓
    Research：不通读项目，围绕任务找入口、调用链、范例，定位最小相关上下文，
       ↓
    Spec（做什么、验收标准、范围外）→ Plan（怎么做，AI 出方案，我审查）→ 存进仓库
       ↓
    Execute：测试先行（Red→Green），我根据 Plan 核对、复跑、变异检查、审核关键代码，提交
       ↓
    Review：新会话依据 review-checklist.md 审查，我来决定修复哪些问题
       ↓
    修复：一次一两条，TDD
       ↓
    Ship：PR + CI



1. 你怎么保证 AI 写的代码质量？
三层：测试先行，先看到失败再实现；我自己复跑检查而不是信 AI 的汇报；再用新会话按清单 Review。另外会做变异检查，故意改坏实现看测试会不会变红，验证测试有效。

2. 全绿就代表没问题吗？
不代表。全绿只说明已有测试没发现问题。所以测试要先红后绿，测试清单来自 Spec 的验收标准而不是照着代码写，再用变异检查验证。测试的价值在于以后改坏时会变红。

3. 为什么要写 Spec，不直接说需求？
对话会漂移，新会话也无法复用。Spec 在仓库里，能转成测试，AI 在新会话里读文件就能接着干。

4. Spec 和 Plan 的区别？
Spec 管做什么，由我决定；Plan 管怎么做，AI 提出我来审。判断方法：换一种实现方式这句话还成立吗？成立属于 Spec，不成立属于 Plan。

5. SDD 和 TDD 的关系？
互补。SDD 管需求层，TDD 管实现层，Spec 里的验收标准会在 Plan 里对应成测试。

6. 这套流程会不会太重？
会，所以按任务风险分级。小改动一条 prompt 加测试先行加自动检查；跨模块或高风险的才走完整的 Spec、Plan、分步执行。流程是为了控制风险，不是仪式。

7. 为什么用新会话做 Review？
写代码的会话带着自己的假设，容易觉得没问题。新会话只看 diff，没有这层偏见。

8. AI Review 的结论你全信吗？
不全信。它会误报也会漏报。我对每条发现问两个问题：是真的吗？在范围内吗？真且在范围内才修，真但在范围外记进 backlog，误报就忽略。

9. 项目很大，AI 读不完怎么办？
本来就不该读完。围绕任务定向调研，用搜索定位入口，沿调用链追踪，找相似功能当范例。结论要求带文件路径，我抽查核对防幻觉，结果存成文件给后面引用。

10. AGENTS.md、Skill、Hook 怎么分工？
AGENTS.md 放长期规则，是建议；Skill 放按需加载的流程，平时只占一行描述；Hook 是确定性执行，用于必须发生的动作。这个项目里我用了前两个，Hook 我了解用途但没配过。

11. 你 Review 发现了什么？
请求体没有大小限制、HTTP 服务器没设超时，都是生产必备项，我各自先补失败测试再修。另外 Review 还暴露出仓库里提交了二进制和 IDE 配置，我补了 .gitignore 并取消跟踪。404/405 返回格式和规则措辞不一致，记进了 backlog。

12. AI 说它做完了，你怎么确认？
对账改动文件是否和 Plan 清单一致，检查 go.mod 没变，在自己环境复跑 make check，看覆盖率，再做变异检查。AI 的环境和我的可能不一致，之前它的环境就找不到 make。


收到需求
│
├─ 先判断：改动牵扯多大？
│   ├─ 几个文件、规则清楚、出错可回退 ──→ 小需求
│   ├─ 有规则要决定 / 多个文件 / 跨模块 / 影响已有调用方 ──→ 大需求
│   └─ 拿不准时可以让AI初步判断要改哪些文件，比预期多就升级为大需求
│
├─【小需求】
│   ├─ 1. 一条 prompt 说清三样：做什么 / 验收标准 / 不能动什么
│   ├─ 2. AI 测试先行：先写失败的测试，再改代码
│   ├─ 3. 我检查：对账改动文件 → 自己跑 make check → 看 diff
│   └─ 4. 提交
│   （不写 Spec，不写 Plan，不单独 Review）
│
└─【大需求】
    ├─ 1. Research：完善上下文
    ├─ 2. 需求澄清：AI 反向提问，我确认
    ├─ 3. Spec：做什么、验收标准、范围外 ──→ 我审，存仓库
    ├─ 4. Plan：怎么做、文件清单 ──→ 我审，存仓库
    ├─ 5. Execute：测试先行，我对账、复跑、审关键代码，提交
    ├─ 6. Review：新会话按清单审，我分类（要修 / 记下来 / 误报）
    ├─ 7. 修复：一次一两条，先写失败测试
    └─ 8. Ship：PR + CI
